# DT-007: Reliability, determinism, and performance sanity checks

| Field | Value |
|---|---|
| Size | S |
| Type | Test-focused feature |
| Requirements | FR-06, NFR-03, NFR-06 |
| Depends on | DT-005, DT-006 |
| Test cases | TC-18, TC-19, plus performance sanity |

## Summary
Add cross-request behavior checks: the service is stateless, deterministic, remains healthy after bad input, and does not wait in real time.

## Scope
- Identical request twice returns equivalent results (API level).
- Invalid request followed by a valid request still succeeds.
- A `FAIL` request does not affect the next independent request.
- `/health` stays 200 after invalid requests.
- Maximum-time request (300 + 120) returns in under 1 second locally, proving simulated time is calculated rather than waited.
- Confirm no module-level mutable state in the simulator or API.

## Acceptance criteria
- Request sequences (invalid -> valid, FAIL -> PASS, valid -> valid) produce the expected independent results.
- Time-bound test uses a generous threshold and no sleeps.
- A seeded defect that introduces shared state or `time.sleep` makes at least one test fail.

## Independent test approach
- Sequence-based `TestClient` tests; the performance check measures only the in-process call duration.

## Definition of done
- Tests are stable (run repeatedly with no flakiness) and require no network or AWS access.

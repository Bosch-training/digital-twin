# DT-005: POST /simulate endpoint (valid requests)

| Field | Value |
|---|---|
| Size | M |
| Type | Feature |
| Requirements | FR-02, FR-03, FR-04 (HTTP contract), FR-06 |
| Depends on | DT-001, DT-002, DT-003, DT-004 |
| Test cases | TC-02, TC-03, TC-04, TC-05, TC-08, TC-09, TC-18, TC-20, TC-21 (API level) |

## Summary
Wire validation (DT-004) and the simulator (DT-002/003) behind `POST /simulate`, returning the documented JSON contract for valid requests.

## Scope
- Endpoint parses the body into the request model, calls the simulator, returns HTTP 200 JSON.
- The route holds no business logic; it only maps the request to the simulator and the result to the response.
- Response shape and field names are fixed and the same for PASS and FAIL.
- Invalid-input handling is only what the framework does by default here; the contractual 400 behavior is DT-006.

## Acceptance criteria
- **Given** the example request in FR-02, **then** the response equals the FR-03 example exactly.
- **Given** `FAIL`, **then** HTTP 200, status `REJECTED`, total equals assembly time.
- Boundary-valid requests (1/300, 1/120) return 200.
- Two identical requests return identical bodies.
- Response contains no fields beyond the documented contract.

## Independent test approach
- `TestClient` tests with the simulator patched with a stub to verify the contract mapping in isolation, plus a few un-stubbed end-to-end checks. Does not require DT-006, CI, or Docker.

## Definition of done
- Contract tests pass; response schema documented in the OpenAPI output.

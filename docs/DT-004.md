# DT-004: Request model and validation rules

| Field | Value |
|---|---|
| Size | M |
| Type | Feature |
| Requirements | FR-02, FR-05 (rules), NFR-01 |
| Depends on | None (validation model only, no HTTP) |
| Test cases | TC-04 to TC-16 (model level) |

## Summary
Define the `/simulate` request model in `app/models.py` and enforce all field rules, independent of HTTP and of the simulator.

## Scope
| Field | Rule |
|---|---|
| `product_id` | string; trimmed; non-empty; max 50 characters |
| `assembly_time_seconds` | strict integer 1-300 inclusive |
| `inspection_result` | exactly `PASS` or `FAIL` |
| `packaging_time_seconds` | strict integer 1-120 inclusive |

- All four fields required.
- Strict typing: strings, decimals, booleans, and null are rejected for time fields (note `True` is an `int` in Python and must be rejected).
- Validation errors identify the failing field in a readable message.

## Out of scope
- HTTP status codes and the error envelope (DT-006), running the simulation.

## Acceptance criteria
- Boundaries accepted: assembly 1 and 300; packaging 1 and 120.
- Rejected: assembly 0 and 301; packaging 0 and 121.
- Rejected: missing field, empty or whitespace-only `product_id`, `product_id` of 51 characters, accepted at 50.
- Rejected: `inspection_result` of `"pass"`, `"MAYBE"`, `""`, null.
- Rejected: time given as `"30"`, `30.5`, `30.0`, `true`, `null`.
- Open question: is `inspection_result` case-sensitive (`pass`)? Proposed default: case-sensitive, reject.

## Independent test approach
- Instantiate the model directly in parametrized unit tests (valid and invalid tables, boundary-value analysis). No server, no simulator.

## Definition of done
- Boundary and equivalence-class tables are in the tests; the model contains no simulation logic.

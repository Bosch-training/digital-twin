# DT-013: AWS deployment (ECS on Fargate)

| Field | Value |
|---|---|
| Size | L |
| Type | Feature (deployment) |
| Requirements | NFR-05, Acceptance criterion 11, Section 9 (AWS target) |
| Depends on | DT-012 (image), DT-011 (CI); DT-014 for verification |
| Test cases | Deployment verification |

## Summary
Deploy the container image to the prepared AWS target (ECS on Fargate, ALB if available) from a GitHub Actions workflow, with no secrets stored in the repository.

## Scope
- Push the image to a registry (for example ECR) and update or register the ECS task definition and service.
- Authenticate GitHub Actions to AWS with OIDC role assumption or repository secrets; never commit credentials.
- Account ID, region, cluster, and service names come from GitHub variables/secrets, not code.
- Deployment gated on a green CI run on the main branch (or manual approval).
- Container logs go to CloudWatch Logs.
- Document teardown/cleanup steps and a cost limit.
- A substitute AWS-hosted container target is acceptable if the lab environment requires it.

## Out of scope
- Autoscaling, multi-AZ high availability, WAF, custom domain, Terraform as a prerequisite.

## Acceptance criteria
- Merge to main triggers build, push, and deployment; the service reaches a healthy state.
- Deployed `GET /health` returns 200 over the public endpoint.
- Container logs are visible in CloudWatch.
- Deployment fails (and does not replace the running service) if the build or tests fail.
- Repository scan shows no credentials or account IDs.

## Independent test approach
- Verify with the smoke tests from DT-014 against the deployed URL. Pipeline wiring can be rehearsed with a dry run or a sandbox AWS account.

## Definition of done
- Successful deployment run link, CloudWatch log screenshot, and cleanup steps documented.

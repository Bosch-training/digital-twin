# DT-006: Consistent HTTP 400 error handling

| Field | Value |
|---|---|
| Size | M |
| Type | Feature |
| Requirements | FR-05 (HTTP behavior), FR-07, NFR-03 |
| Depends on | DT-001 (app), DT-004 (validation rules); DT-005 for the end-to-end checks |
| Test cases | TC-06, TC-07, TC-10 to TC-17, TC-22 (API level) |

## Summary
Map every client-input error to HTTP 400 with a single JSON error envelope, and ensure no internals are leaked.

## Scope
- Error envelope: `{"error": {"code": "INVALID_REQUEST", "message": "<useful text>"}}`.
- FastAPI returns 422 by default for validation errors; override it to return 400 with the envelope above.
- Cover: missing fields, out-of-range values, wrong types, bad `inspection_result`, bad `product_id`, malformed JSON, non-object JSON bodies (array, string, number, null), empty body.
- No stack traces, framework internals, or Pydantic error dumps in responses.
- Unexpected server errors return a generic 500 envelope without internals (details go to logs, DT-008).
- Invalid requests never invoke the simulator.

## Acceptance criteria
- Every invalid category above returns 400 with `error.code` and `error.message` present and non-empty.
- Message names the offending field where applicable (for example `assembly_time_seconds must be between 1 and 300`).
- Response body never contains `Traceback`, file paths, or `pydantic`.
- Simulator is not called for an invalid request (assert via mock).

## Independent test approach
- Parametrized `TestClient` tests posting invalid payloads. The simulator is mocked and asserted not called, so this does not depend on DT-002/003 correctness. Raw-body tests (`content=`) are needed for malformed JSON.

## Definition of done
- All invalid-input test cases pass; error envelope documented (DT-009).
